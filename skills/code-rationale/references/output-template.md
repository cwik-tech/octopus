# Output template

Adapt the structure to the size of the question. Do not force empty sections into a small answer.

## Answer

State the best-supported explanation in a short paragraph. Attribute a single-source rationale rather than presenting it as unquestioned fact.

Include an overall confidence statement and the main reason for that confidence.

## Code anchor

Name the current files, symbols, lines, tests, or configuration that define the behavior being investigated. Briefly explain what the code does now.

## Stated rationale

List explicit historical statements. For each one include:

- the attributed claim;
- a stable citation;
- author or decision owner when relevant;
- date and relation to the change;
- whether shipped behavior matches the statement.

## Supported interpretation

Explain conclusions that require reasoning across facts. Show the inference step and whether the sources are independent.

Skip this section when the stated record answers the question fully.

## Contradictions or competing explanations

Include this section only when material disagreement or ambiguity exists. Give the evidence for and against each explanation. Preserve chronology when the disagreement may reflect a changed decision.

## What remains unknown

Name unanswered parts of the question, missing history, inaccessible or out-of-scope sources, retention limits, and searches that returned no relevant result.

State empty searches narrowly. Include the source, query or identifiers, date range, and access limitation when useful.

## Sources searched

Use a compact list or table containing:

- source or capability;
- what was searched;
- relevant result, no relevant result, unavailable, or out of scope;
- important coverage limitation.

Do not list sources that were merely available but not searched.

## Change constraints

Add this only when the user is preparing to modify the code.

- **Preserve:** constraints or behaviors still supported by evidence.
- **Change:** rationale that is obsolete, contradicted, or no longer applicable.
- **Avoid:** rejected approaches whose failure conditions still hold.
- **Risk:** unknowns that should be resolved or tested before implementation.

Do not turn historical rationale into a permanent requirement automatically. State whether the original constraint still exists.
