### Session: 2026-03-31 — Production readiness gap analysis for a multi-agent orchestration runtime
- **What worked:** Anchoring in a mature adjacent domain (workflow orchestration: Airflow, Temporal, Celery) unlocked concrete, evidence-backed insights that the other agents lacked. Citing specific community-validated lessons (config errors as #1 incident cause, durable execution as architectural not feature question) gave the position credibility and changed sequencing arguments. Coupling previously isolated items (context window management + rate limiting as interdependent, not parallel) added real analytical value. Surfacing the compliance gap (HIPAA/SOC 2/GDPR) as a binary requirement — not a judgment call — was the highest-value contribution the other agents had no frame for.
- **What didn't:** The domain brief structure was not fully executed — value chain mapping and competitive landscape were implicit rather than explicit. The position read more as a list of domain lessons than a synthesized brief with clear confidence ratings and citations. The "Step 2" competitive landscape (LangGraph, CrewAI, AutoGen) was named but not analyzed in depth, missing an opportunity to show what those frameworks do differently in production.
- **Pattern noticed:** When the team is debating sequencing of known items, the highest-value domain contribution is identifying *coupling* between items (X must precede Y because X is a prerequisite) and *categorical misclassification* (this is an architecture question, not a feature gap). Teams default to treating backlog items as independent — domain research breaks that assumption with evidence.
- **For next time:** Open with the domain classification explicitly: "This system belongs to the workflow orchestration domain, not primarily the agentic AI frameworks domain." Stating this early would have set the frame for all subsequent analysis. Also: prepare a two-sentence summary of the closest structural analogy (Celery+Flower) and its known limitations before elaborating — it grounds the entire position immediately rather than building to it.

### Session: 2026-04-01 — Deep research integration architecture for a multi-agent pipeline template
- **What worked:** Applying the Jargon Test to "deep research services" was the highest-value move in the session — exposing that "Gemini Deep Research" is a consumer UI feature (not an enterprise async API), that Kimi has no documented enterprise API, and that the services with stable enterprise access (Perplexity, Tavily) are synchronous. This directly dismantled the Contrarian's and Pragmatist's async execution contract debate, which was well-reasoned but solving a phantom problem. Citing specific framework convergence (LangGraph, CrewAI, AutoGen, LangChain all treat search as a tool, not a provider) as a multi-source pattern provided the structural evidence that the board's preferred framing was categorically wrong. The closing question — "which named service actually has a documented async enterprise API?" — was a concrete falsification test that forced the issue.
- **What didn't:** The position successfully identified the phantom async problem but didn't go far enough in positively proposing what the right architecture was. The Innovator ultimately articulated Alternative 1 (model-selection via existing provider interface) more concisely. The domain-researcher position left the board with a corrected framing but not a clear "here's what to build" recommendation — that gap was filled by others. Also: the competitive landscape section (Step 5) was implicit; explicitly naming that Tavily and Exa are the production-grade tools used in deployed agentic systems — not Gemini DR or Kimi — would have strengthened the position further.
- **Pattern noticed:** The most dangerous errors in architectural discussions come from treating marketing-named product features as engineering-grade API contracts. "Gemini Deep Research," "Kimi Deep Research," "Perplexity Deep Research" are all consumer product names that imply enterprise API equivalents that don't exist. Teams anchor on the brand name and design infrastructure around assumed API semantics. The domain-researcher's role is to break that anchor with API documentation evidence — not intuition or analogy. This pattern will recur whenever a board designs around named external services without verifying their enterprise API maturity.
- **For next time:** After exposing the phantom problem, immediately follow with a concrete positive recommendation: "The minimal thing to ship is X, using Y API, in Z pattern — here is why the current interface already supports it." Don't leave the board with a vacuum after deflating their framing. Also: explicitly score each named service on a two-axis matrix (enterprise API maturity: stable/unstable; interaction model: sync/async) in the opening of the position — this would have made the entire phantom-async argument visual and harder to dismiss.

### Session: 2026-04-04 — Michigan automotive market entry for a Brazilian Industry 4.0 company
- **What worked:** The Jargon Test applied to the product category ("predictive maintenance via motor electrical behavior") exposed the specific domain term (MCSA — Motor Current Signature Analysis) and revealed named US incumbents (SKF, Emerson AMS, ALL-TEST Pro) the board would never have surfaced without domain grounding. Naming the formal OEM qualification pathway (Stellantis STAR, IATF 16949, IEC 62443 OT cybersecurity) with specific timelines (12–18 months) transformed the Pragmatist's runway question from strategic advice into a mathematical constraint: 9-month runway + 18-month qualification = impossible path. This is the highest-leverage contribution domain research makes — converting qualitative concerns into binary constraints. Surfacing the Denso global account as a one-call bridging mechanism (not a 6-month relationship-building exercise) was similarly high-value: it reframed the "Brazilian credentials are irrelevant" assumption into "Brazilian credentials are maximally relevant if routed through the right channel." The Allen-Bradley PLC compatibility flag was the right domain-specific product-market fit question — it is the single most important technical unknown that could invalidate the entire strategy, and it was invisible to all other agents.
- **What didn't:** The competitive landscape section named the incumbents (Rockwell, PTC, Sight Machine) and their entry patterns correctly, but did not produce a clear differentiation verdict. The position identified that Ubivis is likely competitive at Tier 2/3 on price and setup simplicity but not at OEM level — but stopped short of stating the direct implication: the product positioning must be explicitly repositioned away from OEM use cases before any US customer conversation. The position also did not explicitly map the domain to the guild system analogy that the Pattern Matcher developed — a missed opportunity, since the domain researcher's competitive landscape evidence (Sight Machine entered through PwC/Deloitte channel, PTC entered through Ford's PLM relationship) directly supports the structural pattern. The two positions should have been developed jointly.
- **Pattern noticed:** When a board is debating entry strategy for a relationship-driven, insular B2B ecosystem, the domain researcher's highest-value contribution is the *procurement pathway map* — not just "relationships matter" but the specific formal process (qualification timelines, required certifications, security review triggers) that determines what is structurally possible within a given runway. This is not intuition; it is researchable domain knowledge that other agents cannot access without it. The pattern: teams default to treating "relationships" as the only barrier in insular markets, but there are almost always formal qualification processes layered on top of the relationship gate — and the formal process often has a longer timeline than the relationship gate, making it the binding constraint regardless of relationship quality.
- **For next time:** When the domain research reveals a formal qualification process with a specific timeline, state the math explicitly in the opening: "OEM qualification takes 12–18 months. If runway is under 18 months, OEM-direct sales is structurally impossible regardless of strategy quality — the math eliminates it." This frames every subsequent strategy recommendation as constrained by the domain reality, rather than leaving it to other agents to connect the dots. Also: when the Innovator surfaces alternative entry mechanisms, test each one against the domain's formal gatekeeping requirements immediately — e.g., does MMTC partnership accelerate or bypass the IATF requirement? That verification is domain-researcher work, not Innovator work, and doing it in real time would have sharpened the Innovator's alternatives significantly.
