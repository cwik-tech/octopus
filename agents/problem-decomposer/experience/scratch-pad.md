### Session: 2026-03-31 — Production readiness gap analysis for multi-agent orchestration runtime
- **What worked:** Broadcasting a detailed framing with explicit "what's implemented" and "what's documented as remaining" lists gave every board agent a concrete foundation to push against rather than theorize in the abstract. The four-agent selection (Contrarian, Pragmatist, Domain Researcher, Client Lens) produced genuinely distinct lenses that built on each other sequentially — Contrarian reframed the problem space, Pragmatist grounded it in executability, Domain Researcher added structural domain evidence, and Client Lens surfaced the political/organizational prerequisites. The Contrarian's challenge to the initial Analytical+Complicated classification (arguing Complex+Diagnostic instead) was the highest-value move in the session — it shifted the entire board from "list features to build" to "understand what will actually break."
- **What didn't:** The initial classification as Complicated+Analytical was too hasty. The system has feedback loops (agents read/write workspace, outputs feed subsequent agents), non-deterministic execution (LLM outputs vary on retry), and emergent failure modes — all signals of a Complex domain problem. Should have caught this at Layer 1 instead of needing the Contrarian to correct it. Also, the framing presented all 8 documented remaining items as peers without pre-filtering, which caused the board to spend cycles triaging items that were clearly scope expansion (workspace watching, dynamic spawn_team, team registry). Pre-filtering obvious scope expansion before broadcasting would have focused deliberation on the genuinely contested items.
- **Pattern noticed:** "Production readiness" is almost always an ambiguous problem definition masquerading as an analytical question. The board converged on a critical prior question — deployment context (who, what scale, what regulatory environment) — that the original brief didn't answer. This is a recurring pattern: clients frame organizational/strategic questions as technical gap analyses. The decomposer should screen for this at Layer 1 Question 2 (problem definition agreement) by checking whether the key terms in the brief ("production-ready") have a shared definition among all stakeholders. When they don't, the real first sub-problem is stakeholder alignment on the definition, not the gap analysis itself.
- **For next time:** (1) When the problem involves a system with feedback loops and non-deterministic components, default to Complex classification and require evidence to downgrade to Complicated — not the reverse. (2) Pre-filter documented backlogs before broadcasting: separate "things that could break what exists" from "things that would add new capabilities" and only broadcast the contested middle ground for board deliberation. (3) Add a "definition alignment check" as step 0 in any assessment engagement: does the key term in the brief (here, "production-ready") have a single agreed definition among all decision-makers? If not, that's the first sub-problem to route to Client Lens before any technical analysis begins. (4) Consider invoking Money Maker for cost-exposure problems — the uncapped budget issue was a strong commercial angle that no agent fully owned.

### Session: 2026-04-01 — Deep research integration layer architecture for multi-agent pipeline template
- **What worked:** The six-agent board selection (Contrarian, Pragmatist, Domain Researcher, Innovator, First-Principles Fool, Pattern Matcher) was the strongest composition yet. Each agent genuinely occupied distinct territory: Domain Researcher demolished the premise that the named APIs are async at all, First-Principles Fool exposed that "deep research" was never defined, Pattern Matcher provided the OS I/O isomorphism that reframed every competing proposal as layers in a single architecture rather than mutually exclusive options, and Innovator generated three genuinely distinct alternatives (model-selection, pre-execution sprint, accumulating knowledge base) that broke the board out of a convergence trap where all three initial positions shared the same underlying mechanism. The Complicated-to-Complex classification with Generative+Strategic typing held up — no agent challenged the classification itself, which is a first. Including the existing `Provider` interface code in the framing gave agents concrete material to reason against rather than abstract architectural hand-waving.
- **What didn't:** The initial framing accepted the client's vocabulary ("deep research," "integration layer," "domain knowledge") without defining it. First-Principles Fool had to do what the decomposer should have done at Layer 1 Question 2: check whether the key terms have agreed definitions. "Deep research" turned out to be a marketing label leaking into architectural vocabulary — Gemini Deep Research is just grounding-enabled Gemini, Kimi has no enterprise API, and Perplexity is a synchronous 3-15 second call. The entire async execution debate that consumed the Contrarian and Pragmatist was built on a factual error about how these services actually work. The decomposer should have asked the Domain Researcher to verify the API landscape *before* broadcasting — not after the board had already spent cycles designing polling wrappers for services that don't support polling. Also, no agent was specifically tasked with answering Question 3 from the brief (domain knowledge accumulation through memory), which meant it was addressed only as one of three Innovator alternatives rather than receiving focused deliberation.
- **Pattern noticed:** (1) **Solution-space convergence masquerading as disagreement.** Three agents (Contrarian, Pragmatist, Domain Researcher) appeared to disagree on architecture but actually shared an identical underlying mechanism: "route research through the execution stack at runtime." The Innovator was the only agent who noticed this convergence and broke out of it. Pattern: when board agents debate *implementation variants* of the same mechanism, the real architectural choices haven't surfaced yet — invoke the Innovator or Pattern Matcher to expand the solution space before the board narrows prematurely. (2) **Factual premises as architectural load-bearing walls.** The entire async/sync debate collapsed when Domain Researcher proved the named APIs are synchronous. Pattern: when an architectural debate has a factual premise (e.g., "these services take minutes and require polling"), verify the fact before debating the architecture. Route to Domain Researcher first, then broadcast — not in parallel. (3) **The "just another X" trap recurs.** Last session it was "just another provider call" for production readiness; this session it was "just another provider call" for research integration. Both times, the question "is this actually the same kind of thing as what the interface was designed for?" was the pivotal question. The Provider interface was designed for LLM execution, not retrieval — Pattern Matcher's OS I/O analogy (device driver vs. system call) clarified that the interface can serve both purposes at different layers, but only if the semantic mismatch is acknowledged rather than papered over.
- **For next time:** (1) **Verify factual premises before broadcasting.** When the problem statement names specific external services/APIs, dispatch the Domain Researcher first to verify actual API capabilities, latency characteristics, and availability. Only then broadcast to the full board. This prevents the board from designing for phantom constraints (async polling for synchronous APIs, cost caps for services without per-call cost APIs). (2) **Run the First-Principles Fool's "undefined terms" check at Layer 1.** The decomposer should do a terminology audit during Layer 1 Question 2 — identify every term in the brief that sounds precise but isn't operationally defined. "Deep research," "integration layer," "domain knowledge," and "works for any domain" were all load-bearing undefined terms. Surfacing these before broadcasting would have focused the board on definition first, architecture second. (3) **When the board converges on mechanism, invoke divergent agents.** If three agents all propose variants of the same mechanism, that's a signal to invoke Innovator or Pattern Matcher before continuing. Convergence on mechanism is not consensus — it's a narrowed solution space. (4) **Assign explicit ownership of each brief question.** The brief had 5 questions; agents self-selected which to address. Question 3 (domain knowledge accumulation) was under-addressed. Next time, assign at least one agent per brief question to ensure coverage. (5) **The Pattern Matcher's "all three coexist" insight is high-leverage.** When the board debates "A vs. B vs. C," the Pattern Matcher's structural analysis often reveals they're layers in a tiered system, not competing options. Consider invoking Pattern Matcher earlier — after initial positions but before synthesis — to check whether the debate is actually a false choice.

### Session: 2026-04-04 — Cross-border B2B market entry strategy for Brazilian IIoT company into Michigan automotive
- **What worked:** (1) The Layer 1 classification as Complex + Strategic/Diagnostic hybrid was the strongest classification yet — the credibility feedback loop (unknown vendor → no access → no references → stays unknown) and the informal/formal dual gatekeeping structure were correctly identified as Complex domain signals from the start. No agent challenged the classification, which is the second consecutive session where initial classification held. (2) The "Core Tension" framing — naming the mismatch between lowest-trust sales method, highest-trust buyer, and zero local credentials in one sentence — gave every agent a sharp anchor to orient against. This was more effective than the list-based framing in Session 1. (3) The six-agent selection (Contrarian, Pragmatist, Domain Researcher, Client Lens, Innovator, Pattern Matcher) produced the most layered analysis yet. Each agent found genuinely distinct territory: Pragmatist grounded everything in operational feasibility and the runway question; Domain Researcher surfaced two structural barriers the brief didn't mention (OEM qualification timelines, OT cybersecurity gate) and the highest-value asset (Denso global account); Client Lens identified the principal-agent commitment problem as the actual binding constraint; Innovator caught mechanism convergence across all other agents and generated three genuinely different alternatives (MMTC partnership, hire-the-network, adjacent market beachhead); Pattern Matcher's medieval guild isomorphism was the deepest structural insight in three sessions — it revealed the board's strategy debate was actually a track-selection question determined by HQ commitment level. (4) The Innovator's "mechanism audit" is now a proven, repeatable technique. In this session, the Innovator demonstrated that all four board recommendations (Denso call, VW referral, hire Michigan sales rep, Tier 2/3 pilot) shared the identical underlying mechanism: "earn trust through relationships, then sell." This convergence detection forced the board to generate genuinely different options rather than debating implementation variants of the same idea. (5) Client Lens's "champion-able one-page ask" — framing the entire strategy as two phone calls the Brazilian CEO can make in 30 days — was the most actionable single output the board has ever produced. It converted complex strategic analysis into a politically viable, bounded decision request.
- **What didn't:** (1) **The Contrarian agent failed to execute.** It returned a meta-response about its own prompt structure rather than engaging with the problem content. This meant the board's strongest assumption-challenging lens was absent. No agent challenged the fundamental premise: "Should Ubivis enter Michigan automotive at all, or is the target market wrong?" The Innovator's Adjacent Market Beachhead partially addressed this, but it was framed as a sequencing tactic, not as a genuine challenge to the premise. A functioning Contrarian would likely have asked: "Is a 30-person Brazilian SaaS company with zero US customers and a Portuguese website actually ready for any US market entry — or should they be investing in a different expansion geography (Mexico automotive, which shares language and trade agreements) instead of the hardest possible market?" That question was never asked. (2) **The decomposer's Session 2 lesson — "verify factual premises before broadcasting" — was not applied.** The Domain Researcher had to surface the Allen-Bradley PLC compatibility question, the "no competition" claim in the pitch deck, and the MCSA category naming gap during their position statement. These are factual premises that should have been flagged at Layer 1 and sent to the Domain Researcher for verification before the full board spent cycles on strategy. If Allen-Bradley integration doesn't work natively, the entire US market strategy has a product-market-fit blocker that invalidates the go-to-market discussion. (3) **No agent owned the "should they even be doing this?" question.** The brief's framing — "design a viable market entry strategy" — presupposed that entry is the right move. The board accepted this presupposition. But the evidence (Portuguese website after 6 months, zero pipeline, cold email as sole method, unknown budget/team size) could equally support a recommendation to pause US entry, redirect resources to a more accessible market, or restructure the US commitment before any sales motion. The board optimized within the frame rather than challenging whether the frame was correct.
- **Pattern noticed:** (1) **The "problem behind the problem" is now a confirmed three-session pattern.** Session 1: "production readiness" was really about deployment context and stakeholder definition alignment. Session 2: "deep research integration" was really about undefined marketing terms leaking into architecture. Session 3: "market entry strategy" is really about organizational commitment and principal-agent alignment. In every session, the presenting problem (technical/strategic) masks an organizational/political problem that is the actual binding constraint. The decomposer should add a systematic "what's the problem behind this problem?" check at Layer 1, specifically: "If I solve the stated problem perfectly, does the client's situation actually improve? Or is there a prior condition (commitment, alignment, definition, resources) that must be true for the solution to matter?" (2) **Client Lens + Pattern Matcher is the highest-value agent pairing for organizational problems.** Client Lens identifies who holds the real power and what political constraints exist. Pattern Matcher reveals the structural archetype that predicts how the system will behave. Together, they produced the session's core insight: this is a principal-agent commitment problem (Client Lens) that follows the medieval guild admission pattern (Pattern Matcher), and the correct strategy depends entirely on whether the home guild (Brazilian HQ) will write the letter of introduction. Neither agent alone would have reached this. (3) **The Innovator's mechanism audit should be a standard board protocol, not an agent-initiated insight.** In Sessions 2 and 3, the Innovator caught mechanism convergence that the decomposer should have caught during synthesis. When multiple agents propose what sound like different strategies but share the same underlying mechanism, the solution space hasn't actually been explored — the board is debating implementation variants. The decomposer should run a mechanism audit after initial positions: "Do these apparently different recommendations share a common mechanism? If yes, the board needs a divergent option before converging." (4) **Domain Researcher consistently surfaces the "blocking unknown" that restructures the entire strategy.** Session 2: the APIs are actually synchronous. Session 3: Allen-Bradley compatibility is unverified, OEM qualification takes 18 months, and Denso global is the highest-value unactivated asset. Each time, these findings invalidated assumptions the rest of the board was building on. The Domain Researcher should always go first or in parallel with the framing broadcast — never after.
- **For next time:** (1) **When the Contrarian fails, assign the frame-challenging role explicitly to another agent.** The board must never proceed without at least one agent whose job is to challenge the problem's premise and framing. If the Contrarian is unavailable, assign the Pattern Matcher or Innovator to spend their first paragraph challenging "should we even be solving this problem?" before moving to their primary lens. (2) **Institutionalize the mechanism audit as a decomposer responsibility.** After receiving initial positions, before invoking additional agents or synthesizing, the decomposer should check: "Do these positions share a common underlying mechanism?" If yes, explicitly invoke the Innovator with a directive to generate alternatives that use a structurally different mechanism. (3) **For market entry and "how to get in" problems, always add a "should they get in at all?" question to the board framing.** The presupposition that entry is the right move should be tested, not assumed. Frame it as: "One valid output of this board is a recommendation to not enter this market, or to enter a different one first. That recommendation is on the table." (4) **Apply the Domain Researcher-first protocol that was identified in Session 2 but not executed in Session 3.** When the brief contains factual claims about products, markets, or capabilities (PLC compatibility, competitive landscape, API capabilities), dispatch the Domain Researcher first to verify. Only broadcast to the full board after factual premises are confirmed or corrected. This session's Allen-Bradley question and "no competition" claim should have been verified before the Pragmatist and Innovator built strategy on top of them. (5) **The "champion-able one-page ask" format from Client Lens should become a standard synthesis output.** Every board session should produce not just a strategic recommendation but a single, bounded, politically viable ask that the person closest to the problem can carry to the decision-maker. The gap between "correct strategy" and "strategy that gets executed" is almost always a political translation problem, and Client Lens's format bridges it. (6) **Track the Pattern Matcher's structural archetypes across sessions as a reusable library.** Session 2: OS I/O isomorphism (device driver vs. system call). Session 3: medieval guild admission (trust-gated network with non-transferable credentials). These archetypes have explanatory power beyond the sessions that generated them. When a new problem arrives, check it against the existing archetype library before invoking the Pattern Matcher — the right framing may already exist.
